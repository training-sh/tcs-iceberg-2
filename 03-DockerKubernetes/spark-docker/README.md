# Spark in Docker: Ubuntu + Java 11

Build one image and use it for a Spark standalone master and worker. Spark 3.5.9 uses the Hadoop 3 / Scala 2.12 distribution. Java 11 and Python come from Ubuntu packages inside the image; no host Spark or Java installation is needed.

Run Docker commands on a remote Ubuntu VM only, not WSL or a corporate laptop. Use the Docker installation steps in the preceding Day51 notebook. Allow roughly 4 CPUs, 8 GB RAM, and 10 GB free disk for this exercise. Internet access is needed for packages, Spark, and Maven downloads.

## Files

| File | Purpose |
|---|---|
| `Dockerfile` | Ubuntu base, Java 11, Python, Spark, and copied connector JARs |
| `entrypoint.sh` | Run master, worker, or an explicit command in the foreground |
| `download-jars.sh` | Download the pinned connector files into `jars/` |
| `compose.yaml` | Run the same image as two services |
| `.dockerignore` | Keep the build context small while including JARs |
| `.gitignore` | Keep downloaded binaries out of Git |
| `.gitattributes` | Keep shell scripts in Linux line-ending format |

`jars/` is generated by the downloader. It does not need to be committed. This folder is self-contained and can be uploaded to GitHub as part of the course repository or as its own repository. Download the ZIP or clone the repository, then open this folder on the VM. No GitHub URL is hard-coded.

## 1. Download JARs and build

From the course repository root:

```bash
cd Day51/spark-docker
sudo apt update
sudo apt install -y curl ca-certificates
bash download-jars.sh
ls -lh jars/
docker build -t day51-spark:3.5.9-java11 .
docker image ls day51-spark
```

If this folder is the root of its own repository, run the commands from there and omit `cd Day51/spark-docker`. The final dot is the build context. Docker downloads Spark and verifies its SHA-512 checksum during the build. `COPY jars/*.jar /opt/spark/jars/` puts the downloaded connectors into both master and worker images.

```bash
docker run --rm day51-spark:3.5.9-java11 java -version
docker run --rm day51-spark:3.5.9-java11 spark-submit --version
docker run --rm day51-spark:3.5.9-java11 bash -c 'ls /opt/spark/jars/*delta* /opt/spark/jars/*kafka*'
```

Expect Java 11 and Spark 3.5.9. Both roles use the same image tag.

## 2. Start the master manually

```bash
docker network create spark-lab
docker volume create day51-spark-data

docker run -d --init --name spark-master --hostname spark-master \
  --network spark-lab \
  -p 127.0.0.1:8080:8080 -p 127.0.0.1:4040:4040 \
  -v day51-spark-data:/opt/spark/data \
  day51-spark:3.5.9-java11 master
```

Open `http://localhost:8080` through the SSH tunnel below. Before the worker starts, the master shows zero workers.

## 3. Start the worker manually

```bash
docker run -d --init --name spark-worker --hostname spark-worker \
  --network spark-lab \
  -p 127.0.0.1:8081:8081 \
  -e SPARK_MASTER_URL=spark://spark-master:7077 \
  -e SPARK_WORKER_CORES=2 -e SPARK_WORKER_MEMORY=2g \
  -v day51-spark-data:/opt/spark/data \
  day51-spark:3.5.9-java11 worker
docker ps
docker logs spark-worker
```

Wait for a successful registration message and one ALIVE worker in the master UI. The worker offers 2 cores and 2 GB executor memory. This is Spark scheduling capacity, not a Docker memory limit.

## 4. Open the web interfaces

From your local terminal, replace the SSH user and VM address. Keep the connection open:

```bash
ssh -L 8080:127.0.0.1:8080 -L 8081:127.0.0.1:8081 \
    -L 4040:127.0.0.1:4040 user@vm-address
```

| Local browser URL | Interface |
|---|---|
| `http://localhost:8080` | Spark master |
| `http://localhost:8081` | Spark worker |
| `http://localhost:4040` | Active application's driver UI |

Only the VM's loopback ports are published. Port 7077 is the internal Spark master endpoint, not a web page. If the previous Docker exercise is still running, stop its Nginx or Adminer container before reusing ports 8080 and 8081. Links in Spark pages may contain container hostnames; use the forwarded URLs above directly.

## 5. Submit a job

```bash
docker exec -it spark-master spark-submit \
  --master spark://spark-master:7077 --deploy-mode client \
  --conf spark.driver.host=spark-master \
  --conf spark.driver.bindAddress=0.0.0.0 \
  --total-executor-cores 2 --executor-memory 1g \
  /opt/spark/examples/src/main/python/pi.py 10
```

Expect a line beginning `Pi is roughly`. The driver runs in the master container; executors run in the worker. `spark.driver.host` advertises a name the worker can reach. The short job's port 4040 disappears when it finishes.

## 6. Switch to Compose

First stop and remove the two manually started containers so their host ports are free:

```bash
docker stop spark-worker spark-master
docker rm spark-worker spark-master
docker network rm spark-lab
```

Then, from this directory:

```bash
docker compose config -q
docker compose build
docker compose up -d --pull never
docker compose ps
docker compose logs spark-worker
```

The explicit build creates the shared local image before either service starts. The worker starts after the master's UI health check passes; confirm registration in the master UI. Compose creates its own network and a shared data volume. Its volume is separate from `day51-spark-data` used above.

```bash
docker compose exec spark-master spark-submit \
  --master spark://spark-master:7077 --deploy-mode client \
  --conf spark.driver.host=spark-master \
  --conf spark.driver.bindAddress=0.0.0.0 \
  --total-executor-cores 2 --executor-memory 1g \
  /opt/spark/examples/src/main/python/pi.py 10
```

For an interactive application whose UI stays available:

```bash
docker compose exec spark-master pyspark \
  --master spark://spark-master:7077 \
  --conf spark.driver.host=spark-master \
  --conf spark.driver.bindAddress=0.0.0.0 \
  --total-executor-cores 2 --executor-memory 1g
```

At the Python prompt:

```python
spark.range(1, 11).show()
print(spark.sparkContext.master)
```

Keep the shell open while viewing port 4040. Finish with `spark.stop()` and `exit()`. Standalone Python applications use client deploy mode here.

## 7. Connector JARs

| Feature | Included version |
|---|---|
| Delta Spark + storage | 3.3.2, Scala 2.12 |
| Iceberg Spark runtime | 1.10.0 for Spark 3.5 / Scala 2.12 |
| Kafka SQL + token provider | 3.5.9, Scala 2.12 |
| Kafka client + commons-pool2 | 3.4.1 + 2.11.1 |
| Spark Avro | 3.5.9, Scala 2.12 |
| MySQL JDBC | 8.4.0 |
| PostgreSQL JDBC | 42.7.8 |

The Kafka token-provider JAR is included as a connector dependency. Spark already supplies the base runtime libraries. Do not add a second Scala, Spark, or Hadoop runtime alongside them.

For the optional Iceberg S3 and Hadoop S3A connectors:

```bash
bash download-jars.sh --with-s3
docker compose build
docker compose up -d --force-recreate --pull never
```

This adds Iceberg AWS bundle 1.10.0, Hadoop AWS 3.3.4, and AWS Java SDK bundle 1.12.262. Downloading without the option later does not delete previously downloaded JARs. AWS credentials and catalog settings are not included. Keep credentials outside the image.

Copying JARs makes their classes available; it does not configure a Delta/Iceberg catalog, create Kafka brokers, or create JDBC databases. Delta Python helpers are not installed; use Spark SQL/DataFrame APIs or install a matching Python package separately when needed.

## 8. Data and cleanup

Both services mount one named volume at `/opt/spark/data`. Use that path when a job on this single VM needs shared local files. The cluster has no HDFS, YARN, or history server. Worker scratch files are separate from this shared data volume.

```bash
docker compose down
```

This removes the Compose containers and network but retains their data volume. To deliberately erase the Compose data too:

```bash
docker compose down -v
```

After the manual containers have been removed, their separate volume can be deleted with `docker volume rm day51-spark-data` if its contents are no longer needed.

## Troubleshooting

- `COPY jars/*.jar` fails: run `bash download-jars.sh` before building.
- Worker not registered: inspect both logs; confirm the master address and shared network.
- Driver connection fails: submit inside the master container with the supplied driver host settings.
- Port in use: stop the earlier lab, or change the host-side mapping and SSH forwarding together.
- `bad interpreter` after editing on Windows: save `.sh` files with LF endings. The repository attributes preserve LF on checkout.
- A build download fails: check VM internet access and rerun. Do not disable TLS certificate verification.
